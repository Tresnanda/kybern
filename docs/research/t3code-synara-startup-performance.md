# T3 Code and Synara startup-performance research

Research captured 2026-09-04 against these upstream revisions:

- [T3 Code `f559fe0`](https://github.com/pingdotgg/t3code/commit/f559fe0ba6fb5950bd14a2404f10b9c94b33f696)
- [Synara `562c5fe`](https://github.com/Emanuele-web04/synara/commit/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1)
- Kybern local revision `68192f6`

Only official upstream repositories and their history were used. Line links are pinned to the revisions above so the findings remain reproducible.

## Executive answer

Kybern's observed two-second-plus empty window is not primarily a SQLite or React problem. The current boot path invokes the same full refresh twice, and neither invocation publishes projects or threads until the slowest member of one `Promise.all`—live provider discovery—finishes. The local measurements make the separation unusually clear: ordinary shell RPCs take 7–13 ms, while `providers.list` takes 3.84 seconds once and 4.66 seconds under the duplicated startup work.

The strongest upstream pattern is therefore **staged hydration**:

1. Render immediately.
2. Start one connection attempt immediately.
3. Hydrate a narrow persisted shell snapshot independently of provider discovery.
4. Publish each usable state slice as soon as it arrives.
5. Seed provider status from a stable cache and refresh/probe in the background, with in-flight request coalescing.

For harness TTFT, Kybern already has two important fast paths: the draft RPC fuses thread creation with the first message, and live agent sessions are reused for follow-ups. The highest-confidence remaining wins are to stop repeating executable/model probes, preserve Git's index stat cache during the pre-prompt checkpoint, and pool OpenCode servers. Checkpoint correctness should remain a hard barrier before the prompt is dispatched. Session startup and checkpoint capture may be overlapped because both precede dispatch, but that is a Kybern experiment—not a pattern proven safe by either upstream—and needs cancellation and filesystem-write auditing.

## Findings at a glance

| Area | Kybern today | Upstream pattern | Recommended move |
| --- | --- | --- | --- |
| Initial shell data | Two `loadAll` calls; one all-or-nothing `Promise.all` includes provider probes | Synara streams a narrow shell snapshot; T3 Code restores a versioned IndexedDB shell cache | Remove the duplicate call; split shell hydration from provider/catalog work |
| Window timing | Tauri endpoint resolution waits for daemon validation/readiness | Synara opens the packaged window before backend readiness; T3 Code keeps a static splash and cache-first runtime state, although its main desktop window still waits for primary backend readiness | Show the shell/splash immediately; optionally add bounded shell/thread cache in a second phase |
| Provider status | `providers.list` runs all live driver probes and model discovery | Both upstreams expose stable state immediately and run expensive probes in the background; Synara persists status cache | Make catalog/status reads cheap; cache probe results and load models lazily |
| First message | Fused `threads.create` with optional `message`; then session spawn → checkpoint → provider send | T3 Code also uses one fused first-turn RPC; both projects retain live sessions | Keep the fused RPC and measure inside the background turn path |
| Follow-ups | Reuses an in-memory per-thread session | Both upstreams retain sessions; Synara also bounds idle retention and OpenCode server lifetime | Keep reuse; add pooling/idle policy only where resource pressure justifies it |
| Checkpoint | Fresh temporary index, `read-tree HEAD`, `add -A` | Synara copies and refreshes the working index so unchanged files keep their stat cache | Adopt the copied-index technique; do not move prompt dispatch ahead of the completed baseline |

## Exact status of four deferred techniques

For this classification, **implemented** means the pinned code has the mechanism itself, **analogous** means it has a related optimization with materially different lifetime or ordering, and **absent** means the inspected startup/turn path has no equivalent. A “warm pool” means a process shared across logical thread sessions or held ready for a future session; merely retaining the active process for the same thread is session reuse, not a pool.

### 1. Provider-specific warm pools

- **T3 Code — implemented for OpenCode discovery/text generation, analogous/absent for chat harnesses.** `OpenCodeServerOwner` owns one lazy shared server per provider instance and retains it for 30 seconds after the last borrower ([`OpenCodeServerOwner.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/OpenCodeServerOwner.ts#L11-L30), [`OpenCodeServerOwner.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/OpenCodeServerOwner.ts#L85-L175)). Driver wiring constructs the chat adapter separately, then provides the owner only to text generation and provider-status checking ([`OpenCodeDriver.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Drivers/OpenCodeDriver.ts#L126-L151)); provider status borrows it to load inventory ([`OpenCodeProvider.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/OpenCodeProvider.ts#L477-L503)). The chat adapter instead says each session scope tears down its spawned OpenCode server and starts a server inside a new session scope ([`OpenCodeAdapter.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/OpenCodeAdapter.ts#L975-L989), [`OpenCodeAdapter.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/OpenCodeAdapter.ts#L2448-L2490)). T3 otherwise retains active per-thread sessions for warm follow-ups and reaps them after 30 minutes ([`ProviderSessionReaper.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/ProviderSessionReaper.ts#L13-L15), [`ProviderSessionReaper.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/ProviderSessionReaper.ts#L35-L100)); Codex stores one runtime per thread ([`CodexAdapter.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/CodexAdapter.ts#L1993-L2138)). So provider-process pooling exists, but it does not reduce a new chat thread's harness spawn at this revision.
- **Synara — implemented narrowly.** OpenCode uses a real keyed, ref-counted server pool: it starts lazily on first use, reuses an existing compatible process, and retains it for a five-minute idle TTL ([`opencodeRuntime.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/opencodeRuntime.ts#L57-L104), [`opencodeRuntime.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/opencodeRuntime.ts#L1175-L1244)). Codex also reuses a per-working-directory **discovery** app-server for a 15-second burst window, but that process serves catalog/auth queries rather than user turns ([`codexAppServerManager.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/codexAppServerManager.ts#L320-L323), [`codexAppServerManager.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/codexAppServerManager.ts#L2723-L2845)). Other turn runtimes use retained per-thread sessions with a ten-minute idle policy, which is analogous session reuse rather than proactive pooling ([`ProviderService.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderService.ts#L114-L120), [`ProviderService.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderService.ts#L2694-L2759)).

### 2. Parallel harness spawn and pre-turn checkpoint

- **T3 Code — implemented structurally, without a coordinated join.** `CheckpointReactor` and `ProviderCommandReactor` subscribe to the same turn-start domain stream through separate workers ([`CheckpointReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/CheckpointReactor.ts#L924-L977), [`ProviderCommandReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1760-L1792)). One worker captures the baseline while the other builds the send request—including `ensureSessionForThread` ([`ProviderCommandReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L829-L846))—so cold spawn/handshake and Git capture can overlap. This is not a `Promise.all`-style pair that is joined before send.
- **Synara — absent for spawn versus checkpoint; analogous only inside baseline capture.** The normal turn path first awaits `ensureSessionForThread`, then later constructs and awaits `capturePreTurnBaselines` ([`ProviderCommandReactor.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L2000-L2023), [`ProviderCommandReactor.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L2271-L2343)). It does run the Git checkpoint and non-Git Studio baseline concurrently with each other (`concurrency: 2`), but harness startup has already completed.

### 3. Provider send before checkpoint completion

- **T3 Code — implemented as a non-gated race, not a guaranteed send-first order.** The checkpoint worker asynchronously captures the baseline ([`CheckpointReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/CheckpointReactor.ts#L662-L721)), while the independent provider worker can fork `sendTurn` after session preparation without awaiting a checkpoint receipt ([`ProviderCommandReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1413-L1433)). Production `RuntimeReceiptBus` retains/broadcasts nothing and its `publish` is a no-op, so it supplies no hidden fence ([`RuntimeReceiptBus.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/RuntimeReceiptBus.ts#L1-L25)). Therefore send is allowed to win the race, especially for a warm follow-up, but the code does not require it to. A runtime `turn.started` event triggers another idempotent baseline check ([`CheckpointReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/CheckpointReactor.ts#L482-L530)); that is recovery, not a pre-mutation fence.
- **Synara — absent for normal queued turns and reviews.** Its source explicitly says both baselines must finish before provider execution, then awaits them before `startReview` or the queued `sendTurn` path ([`ProviderCommandReactor.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L2286-L2316), [`ProviderCommandReactor.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L2328-L2343)). `dispatchMode === "steer"` is the explicit exception and bypasses this capture, so the statement should not be generalized to mid-turn steering.

### 4. Persistent desktop shell cache

- **T3 Code — implemented, with a cold-window caveat.** The desktop renderer's IndexedDB stores shell snapshots and bounded thread windows; shell state hydrates into an explicit `cached` state before authoritative HTTP/sequence reconciliation ([`storage.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/web/src/connection/storage.ts#L36-L64), [`shell.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/shell.ts#L30-L98), [`shell.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/shell.ts#L181-L267)). Thread persistence is bounded and skipped while a turn is running ([`threads.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/threads.ts#L43-L50), [`threads.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/threads.ts#L255-L291)). However, the main desktop window is still created only after backend readiness, so this cache shortens post-mount hydration/reconnect; it does not display stale shell data while the daemon is still cold-starting ([`DesktopWindow.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/desktop/src/window/DesktopWindow.ts#L799-L884)).
- **Synara — absent as a domain shell cache; analogous only in perceived-startup behavior.** Its renderer persistence module explicitly stores project-only UI preferences—expanded projects, order, and local names—not project/thread shell entities or transcripts ([`storePersistence.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/web/src/storePersistence.ts#L1-L14), [`storePersistence.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/web/src/storePersistence.ts#L75-L131)). Synara instead opens the window before backend readiness and hydrates a narrow live shell snapshot once connected. That can improve perceived launch, but it cannot show prior shell data offline or before the backend responds.

## 1. App-open and persisted-data visibility

### Kybern's current critical path

The renderer starts `boot()` before mounting React, which is good, but the boot routine awaits endpoint resolution before constructing the WebSocket client. On socket open it calls `loadAll`; the initial subscription's `onResubscribed` callback calls `loadAll` again ([`main.tsx`](../../apps/desktop/src/main.tsx#L35), [`state/rpc.ts`](../../apps/desktop/src/state/rpc.ts#L46-L72)).

`loadAll` waits for daemon info, providers, projects, threads, and settings in one `Promise.all`, then performs a single store update ([`state/rpc.ts`](../../apps/desktop/src/state/rpc.ts#L74-L108)). This makes the provider catalog part of the minimum path to display already-persisted projects and threads.

On the daemon, `providers.list` probes every driver concurrently but does not return until every probe completes ([`rpc.rs`](../../crates/kybern-daemon/src/rpc.rs#L41-L85)). For Codex, one probe runs `codex --version` and starts a separate app-server for `model/list`; the result is not cached ([`codex.rs`](../../crates/kybern-drivers/src/codex.rs#L54-L120), [`codex.rs`](../../crates/kybern-drivers/src/codex.rs#L206-L252)). OpenCode likewise starts commands for discovery ([`opencode.rs`](../../crates/kybern-drivers/src/opencode.rs#L35-L110)).

The desktop shell adds another cold-start gate: endpoint resolution validates an existing daemon, or starts one and polls before returning the URL ([`src-tauri/src/lib.rs`](../../apps/desktop/src-tauri/src/lib.rs#L144-L186)). The daemon itself opens storage and awaits restart recovery before binding the listener and publishing its port ([`state.rs`](../../crates/kybern-daemon/src/state.rs#L45-L79), [`main.rs`](../../crates/kybern-daemon/src/main.rs#L40-L80)).

These source paths agree with the local timing evidence supplied for this investigation:

- `providers.list`: 3.84 s for one request; 4.66 s when startup duplicates it.
- Core shell RPCs: 7–13 ms.

The measurements are directional rather than a benchmark distribution, but the gap is large enough to identify the critical-path mistake.

### Synara: show first, hydrate a narrow stream, enrich later

Synara explicitly coordinates the first packaged window **without waiting for backend readiness**. It creates the window, observes backend readiness in the background, and only uses readiness to manage recovery/failure behavior ([`initialBackendWindowOpen.ts`, `openInitialBackendWindow`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/desktop/src/initialBackendWindowOpen.ts#L22-L58)). Its main process reserves the backend endpoint before spawn, while readiness races a stdout signal and `/health` rather than withholding the endpoint from the renderer ([`main.ts`, `reserveBackendEndpoint` and `waitForBackendWindowReady`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/desktop/src/main.ts#L656-L694)). The preload bridge returns that WebSocket URL synchronously ([`preload.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/desktop/src/preload.ts#L16-L22)).

Once JavaScript loads, transport construction immediately starts a session/reconnect loop ([`wsTransport.ts`, constructor](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/web/src/wsTransport.ts#L698-L762)). Renderer hydration is not gated on provider refresh or even on the later welcome callback: scoped shell/detail subscriptions are started independently ([`__root.tsx`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/web/src/routes/__root.tsx#L2113-L2142), [`__root.tsx`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/web/src/routes/__root.tsx#L2214-L2237)).

The server supplies a deliberately narrow shell projection rather than a full application snapshot ([`wsRpc.ts`, `subscribeShell`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/wsRpc.ts#L983-L1034), [`ProjectionSnapshotQuery.ts`, `getShellSnapshot`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts#L2370-L2436)). The live-stream protocol attaches live delivery before reading the snapshot and then closes the high-water gap, so making startup fast does not introduce a lost-event window ([`wsSnapshotLiveStream.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/wsSnapshotLiveStream.ts#L68-L76), [`wsSnapshotLiveStream.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/wsSnapshotLiveStream.ts#L106-L200)).

Synara recently fixed this exact class of amplification. [Commit `ac07bdd`](https://github.com/Emanuele-web04/synara/commit/ac07bddf225d1faaa484b25a82e7d42111754c44) reports that a large database fetched its shell snapshot three times and replayed 651 dead rows. Coalescing to one fallback and pruning replay work reduced warm boot-to-listen from 1.06 s to 0.53 s in the commit's median-of-three measurements. The numbers are specific to Synara's test database; the architectural lesson for Kybern is to make fallback refresh single-shot and observable.

Synara also removes provider probing from startup. Provider health loads persisted status files in parallel and seeds a stable in-memory snapshot ([`ProviderHealth.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderHealth.ts#L2100-L2148)). Repeated refreshes are coalesced onto one in-flight fiber ([`ProviderHealth.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderHealth.ts#L2490-L2546)); ordinary status reads only read the stable snapshot ([`ProviderHealth.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderHealth.ts#L2784-L2793)). The on-disk cache is explicitly a restart hint rather than an authoritative truth ([`providerStatusCache.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/providerStatusCache.ts#L1-L6)). UI-driven provider update checks are delayed ten seconds and then run hourly ([`providerUpdates.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/web/src/providerUpdates.ts#L13-L17)).

### T3 Code: bounded cache first, authoritative stream second

T3 Code persists its shell projection in IndexedDB. `makeEnvironmentShellState` loads the cache first and exposes an immediate `cached` state, while persistence is debounced through a size-one sliding queue so a burst does not serialize redundant writes ([`shell.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/shell.ts#L30-L98)). A new live session refreshes an authoritative HTTP snapshot before cursor resume; the ordering prevents stale cached data from overwriting newer live data ([`shell.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/shell.ts#L181-L267)). Its documented connection model deliberately separates transport state from shell and thread synchronization, allowing cached data to remain useful offline ([`connection-runtime.md`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/docs/internals/connection-runtime.md#L84-L118)).

Thread caching is bounded rather than a mirror of the whole transcript: the initial window targets the last ten user turns and roughly 100 KB compressed ([`threads.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/threads.ts#L43-L50)). It restores the cached thread and sequence before resuming ([`threads.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/threads.ts#L129-L209)), does not persist a half-streamed `starting`/`running` state ([`threads.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/threads.ts#L255-L291)), and falls back to a capped snapshot when resume cannot bridge the sequence ([`threads.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/client-runtime/src/state/threads.ts#L534-L645)). IndexedDB schema versioning prevents an older frontend from interpreting incompatible cache windows ([`storage.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/web/src/connection/storage.ts#L468-L584)).

T3 Code also separates cheap provider state from enrichment. Its managed-provider layer publishes a lightweight initial snapshot, starts enrichment in the background, and demand-gates periodic refresh ([`makeManagedServerProvider.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/makeManagedServerProvider.ts#L39-L75), [`makeManagedServerProvider.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/makeManagedServerProvider.ts#L101-L180), [`makeManagedServerProvider.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/makeManagedServerProvider.ts#L212-L293)). The registry subscribes before taking its snapshot and states that provider probes must not block layer construction ([`ProviderRegistry.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/ProviderRegistry.ts#L541-L683)).

Its daemon startup also avoids reconstructing full transcripts. It catches projections up and loads a lightweight command read model whose thread entries intentionally omit messages, activities, and checkpoints ([`OrchestrationEngine.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L372-L379), [`ProjectionSnapshotQuery.ts`, `getCommandReadModel`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProjectionSnapshotQuery.ts#L1990-L2196)). The merged [PR #2204](https://github.com/pingdotgg/t3code/pull/2204) reports approximately 47% faster startup and 150–300 MB less memory on persisted real-world state. Those figures are upstream's workload, but the projection boundary is directly relevant if Kybern's restart recovery grows with transcript history.

There is one important applicability caveat. Unlike Synara, T3 Code's primary desktop path waits for backend readiness before creating the main window ([`DesktopApp.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/desktop/src/app/DesktopApp.ts#L144-L226), [`DesktopWindow.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/desktop/src/window/DesktopWindow.ts#L799-L884)). Its cache-first state is still valuable for reconnects and renderer hydration, but Synara is the direct precedent for showing the packaged window before the daemon is ready. T3 Code does reduce perceived blank time once the renderer starts: its static splash remains until auth/runtime and lazy route chunks are ready ([`main.tsx`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/web/src/main.tsx#L43-L78)).

T3 Code also disables Chromium `backgroundThrottling` while its initially hidden window boots, then reenables it after first reveal. The source explains that otherwise hidden-window timers can be coalesced to roughly one second and animation frames can stop ([`DesktopWindow.ts`, window creation](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/desktop/src/window/DesktopWindow.ts#L332-L388), [`DesktopWindow.ts`, first reveal](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/desktop/src/window/DesktopWindow.ts#L746-L764)). Tauri/WebView behavior is not identical, so this is a profiling prompt rather than a direct port.

### Recommended Kybern sequence

The smallest, highest-confidence change is:

1. Give the connection generation one owner for initial hydration. A successful open and an initial subscribe acknowledgement must not both schedule a full refresh.
2. Replace `loadAll` with a shell-critical request (`daemon.info`, projects, threads, and locally available settings) plus independent enrichment requests.
3. Commit shell state as soon as it resolves. Provider state should begin as `unknown` or a cached last-known value, then update separately.
4. Split provider **availability** from provider **catalogs**. Cache cheap executable/version results with a TTL and executable fingerprint, coalesce concurrent probes, and fetch models/skills only when their picker opens or an explicit refresh is requested.
5. Instrument launch → endpoint known → socket open → first shell state committed → provider state committed. Include connection generation and refresh reason so duplicate work is visible.

Opening the window immediately with a connecting shell is the next step. A T3-style IndexedDB shell/recent-thread cache is a stronger second phase, not a prerequisite for eliminating the measured delay. It introduces cache schema, staleness, logout/data-directory isolation, and partially streamed-turn rules that should be designed explicitly.

## 2. Harness boot and TTFT

### Current Kybern ordering

`threads.create` already accepts an optional first message. The daemon creates the thread/worktree, persists it, and enqueues the message in the same RPC ([`Draft.tsx`](../../apps/desktop/src/views/Draft.tsx#L218-L226), [`state/rpc.ts`](../../apps/desktop/src/state/rpc.ts#L271-L296), [`orchestrator.rs`](../../crates/kybern-daemon/src/orchestrator.rs#L180-L231)). There is no client-side create-then-send waterfall to remove.

Once accepted, Kybern runs a background turn in this order: ensure/spawn the agent session, capture the pre-turn checkpoint, then call `send_message` ([`orchestrator.rs`](../../crates/kybern-daemon/src/orchestrator.rs#L297-L358)). Existing sessions are retained in memory and reused ([`orchestrator.rs`](../../crates/kybern-daemon/src/orchestrator.rs#L715-L755)). Codex cold startup launches one app-server, performs `initialize`/`initialized`, then `thread/start` or `thread/resume`; follow-ups go directly to `turn/start` ([`codex.rs`](../../crates/kybern-drivers/src/codex.rs#L279-L364), [`codex.rs`](../../crates/kybern-drivers/src/codex.rs#L1287-L1319)).

The supplied historical aggregates put pre-prompt checkpoint plus spawn at 0.987 s for Claude (`n=1`), 1.224 s average for Codex (`n=2`), and 3.217 s average for OMP (`n=5`). Warm follow-ups were 0.654 s for Claude (`n=1`) and 0.878 s average for Codex (`n=3`). These samples are too small for regression thresholds, but they show that follow-ups already benefit from session reuse and that OpenCode/OMP cold setup deserves separate attention.

### Process reuse and discovery

Synara holds live provider sessions and takes a direct fast path when one exists; startup/recovery only runs when there is no usable live session ([`ProviderService.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderService.ts#L1601-L1672), [`ProviderService.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderService.ts#L2089-L2140)). It reaps only idle, ready, resumable sessions with no native background tasks; the default idle retention is ten minutes ([`ProviderService.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderService.ts#L114-L120), [`ProviderService.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/Layers/ProviderService.ts#L2694-L2759)). This is mainly a resource-bound policy; Kybern's current indefinite in-process reuse is already faster for an immediate follow-up.

Synara's Codex manager caches a successful `codex --version` result for ten minutes, never caches failure, coalesces concurrent callers, and invalidates when the executable fingerprint changes ([`codexAppServerManager.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/codexAppServerManager.ts#L4280-L4355)). Cold start deliberately omits `model/list` from the startup handshake ([`codexAppServerManager.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/codexAppServerManager.ts#L1046-L1149)). T3 Code likewise memoizes command-path resolution—including misses—for 30 seconds because PATH scans can cause hundreds or thousands of filesystem probes ([`shell.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/shared/src/shell.ts#L499-L527), [`shell.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/packages/shared/src/shell.ts#L566-L627)).

For OpenCode, Synara pools server processes by connection key, ref-counts users, and keeps an unused process alive for a five-minute TTL ([`opencodeRuntime.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/opencodeRuntime.ts#L57-L104), [`opencodeRuntime.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/provider/opencodeRuntime.ts#L1175-L1244)). Kybern currently starts `opencode serve` per session ([`opencode.rs`](../../crates/kybern-drivers/src/opencode.rs#L1-L7), [`opencode.rs`](../../crates/kybern-drivers/src/opencode.rs#L177-L308)). A shared keyed server is the most direct upstream-backed response to the slower OMP samples.

T3 Code's Codex adapter also retains a runtime per live session and sends follow-ups through that runtime ([`CodexAdapter.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/CodexAdapter.ts#L1993-L2138), [`CodexAdapter.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/CodexAdapter.ts#L2172-L2218)). Its orchestration returns an existing session unless provider/runtime mode, working directory, provider instance, or model has changed ([`ProviderCommandReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L566-L827)). One caution is that configured MCP state triggers a synchronous `config/mcpServer/reload` before each Codex turn ([`CodexSessionRuntime.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2301-L2312)); Kybern should not introduce an equivalent unconditional follow-up barrier.

### Checkpoint timing and Git work

Synara preserves the correctness boundary: it resolves the agent session first, builds the Git checkpoint and Studio baseline in parallel, waits for both, and only then dispatches the provider request ([`ProviderCommandReactor.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L2000-L2023), [`ProviderCommandReactor.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L2271-L2343)). This is the safe ordering to retain: once the prompt reaches the agent, early tool activity can mutate the worktree and invalidate a concurrently captured "before" state.

The valuable optimization is inside checkpoint capture. Kybern creates a fresh temporary index and runs `read-tree HEAD`, `add -A`, `write-tree`, and `commit-tree` ([`kybern-git/src/lib.rs`](../../crates/kybern-git/src/lib.rs#L120-L151)). That fresh index has no working-index stat cache, so `git add -A` must rediscover unchanged files. Synara instead copies the repository's current index into its temporary `GIT_INDEX_FILE`, refreshes it, and hashes only changed paths ([`CheckpointStore.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/checkpointing/Layers/CheckpointStore.ts#L92-L97), [`CheckpointStore.ts`](https://github.com/Emanuele-web04/synara/blob/562c5fea77cff1dacb29d5e6216ed94a05f1b6a1/apps/server/src/checkpointing/Layers/CheckpointStore.ts#L162-L205)). The implementation should continue using a private index so it never stages user changes in the real index.

It may be possible to begin session startup and checkpoint capture concurrently, then join both before provider send. Neither pinned upstream implements that exact ordering: Synara is explicitly serial at the session/checkpoint boundary, and T3 Code's provider path does not establish it as a general checkpoint optimization. Treat it as a measured experiment. Before adoption, verify that merely starting each driver cannot mutate the worktree, that cancellation closes a half-started session, and that approval/background recovery cannot race the baseline.

T3 Code makes a different tradeoff: its `CheckpointReactor` and `ProviderCommandReactor` consume the same turn-start domain event through independent queues. The checkpoint worker captures a pre-turn baseline asynchronously ([`CheckpointReactor.ts`, pre-turn baseline](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/CheckpointReactor.ts#L662-L721), [`CheckpointReactor.ts`, subscriptions](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/CheckpointReactor.ts#L924-L977)), while the provider worker independently ensures a session and forks `sendTurn` ([`ProviderCommandReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1413-L1433), [`ProviderCommandReactor.ts`, worker](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1760-L1792)). A later runtime `turn.started` event performs another idempotent baseline check ([`CheckpointReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/CheckpointReactor.ts#L482-L530)). There is no explicit baseline-before-provider-send ordering guarantee. Adopting that design would take checkpoint work off TTFT, but it would also change Kybern's rewind guarantee unless the baseline can be proven to precede every provider mutation. For Kybern's current semantics, Synara's barrier is the safer precedent.

### First-turn transport

T3 Code uses one `thread.turn.start` request for thread creation, worktree preparation, and the first message, avoiding a client create/send waterfall ([`ChatView.tsx`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/web/src/components/ChatView.tsx#L6636-L6692)). It renders the user message optimistically first ([`ChatView.tsx`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/web/src/components/ChatView.tsx#L6515-L6546)) and forks first-turn title/branch generation off the provider path ([`ProviderCommandReactor.ts`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1286-L1318)). Kybern already fuses creation and the first message. Its UI should add optimistic echo only if the event projection does not already make acceptance immediate; it will improve perceived latency, not actual model TTFT.

The fused RPC does not make every server step parallel: T3 Code still sequences thread creation, prior-incarnation cleanup, optional worktree fetch/create, setup script, and final turn dispatch ([`ws.ts`, `dispatchBootstrapTurnStart`](https://github.com/pingdotgg/t3code/blob/f559fe0ba6fb5950bd14a2404f10b9c94b33f696/apps/server/src/ws.ts#L939-L1152)). This is a useful diagnostic distinction for Kybern: after network waterfalls are removed, worktree setup needs its own span and may be the remaining first-message bottleneck.

## Prioritized implementation plan

### P0: remove known critical-path work

1. Deduplicate startup hydration and give it a connection-generation guard.
2. Commit projects/threads/settings without waiting for `providers.list`.
3. Return cached provider availability immediately; coalesce and background-refresh live probes.
4. Add spans for provider executable resolution, version probe, model discovery, process spawn, protocol handshake, checkpoint, provider send acknowledgement, and first output event.

These changes directly target a measured multi-second blocker and require no client-side durable cache.

### P1: reduce cold first-turn work

1. Preserve the working index stat cache in Kybern's private checkpoint index; benchmark clean, small-dirty, and large-dirty repositories.
2. Cache executable/version discovery with TTL, in-flight coalescing, and executable fingerprint invalidation. Do not cache failures for long.
3. Remove model/skill catalog discovery from provider health and session startup; load it on picker demand.
4. Pool OpenCode/OMP servers by compatible executable/config/data-directory key, with refcounts and an idle TTL. Keep logical thread sessions separate.

### P2: perceived launch and experimental overlap

1. Open the desktop window immediately with a useful connecting shell.
2. If immediate offline content is desired, add a versioned, bounded cache for the shell and recent thread windows; never persist an in-flight transcript as settled.
3. Experiment with checkpoint and session-start overlap, but join both before prompt dispatch and keep the serial path as a fallback.

## Measurement and acceptance

Do not use one "TTFT" bucket. Record these timestamps with provider, cold/warm state, repository size, and connection generation:

1. App launch → endpoint available.
2. Endpoint → WebSocket open.
3. WebSocket open → first projects/threads store commit.
4. Provider refresh start → each individual probe → stable provider update.
5. Send click → RPC accepted / optimistic message visible.
6. Accepted → process spawned.
7. Spawned → protocol initialized / session ready.
8. Accepted → checkpoint complete.
9. Ready and checkpointed → provider turn accepted.
10. Provider turn accepted → first model output event.

Report cold first turn and warm follow-up separately. For app open, a regression test should assert that an intentionally slow provider probe cannot delay the first shell commit, and that one connection generation triggers no more than one shell snapshot request. For checkpoints, compare resulting trees/commits against the existing implementation before using speed as the deciding metric.

## Conclusions and caveats

- The fastest immediate fix is architectural, not micro-optimization: provider discovery cannot remain in the shell hydration barrier.
- Synara is the clearest model for immediate window creation, narrow live-first shell streams, persisted provider status, and Git-index-aware checkpoints.
- T3 Code is the clearest model for versioned bounded client caches and explicit cached/synchronizing/live state.
- Both reinforce live session reuse. Synara adds a concrete shared-server pattern for OpenCode.
- Kybern already matches T3 Code's fused first-message RPC, so splitting or re-fusing that path would be churn without a demonstrated gain.
- A pre-prompt baseline must finish before provider execution. Parallelizing baseline capture with session startup is plausible but remains an inference to validate, not an upstream guarantee.
